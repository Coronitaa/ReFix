# ReFix AutoDeploy & Re:Goldberg LAN - Deployment Audit Report

This report presents an exhaustive audit of the `ReGoldberg` deployment ecosystem, covering the auto-deployment scripts, proxy DLL behavior, network discovery strategies, registry interactions, and portable installation logic.

## 1. AutoDeploy Workflow (`AutoDeploy.bat`)
`AutoDeploy.bat` serves as the primary user-facing orchestrator. Its responsibilities include:
*   **Target Selection & Game Detection:** Prompts for the game directory and executable, employing `detect_game.ps1` to heuristically identify the engine (Unity, Unreal, Godot, Native), game name, and `AppId`.
*   **Mode Selection:** Allows selecting between **Valve Mode** (WAN ReFix Online using Steam SDR via AppId 480) and **Goldberg Mode** (Offline/LAN emulation without Steam).
*   **Legacy Configuration Handling:** Notably, for **Valve Mode**, `AutoDeploy.bat` overwrites the `ReFix.ini` configuration file in the target directory using a legacy template. In contrast, for **Goldberg Mode**, it preserves the highly-detailed UNAE v3.0 `ReFix.ini` natively generated by `deploy_helper.ps1`.
*   **WinMM Injection:** Copies `winmm.dll` proxy for Valve mode, skipping it for Goldberg LAN mode.

## 2. Deployment Helper Logic (`deploy_helper.ps1`)
The `deploy_helper.ps1` subsystem is the core workhorse, executing engine-specific file manipulations and generating configurations.
*   **UNAE (Universal Network Arbitration Engine) Topology Detection:**
    Analyzes binaries in the target directory (`PhotonRealtime.dll`, `nanosockets.dll`, `Mirror.dll`, etc.) and `global-metadata.dat` strings to identify network architecture:
    *   **Topology A:** Direct Sockets (P2P / LAN / SDR).
    *   **Topology B:** Multiplexed Hybrid (EOS P2P / Mirror / Fusion).
    *   **Topology C:** Strict Cloud-Relay (PUN 2 / Photon Voice), which strictly disables direct P2P routing.
*   **Dynamic Proxies & Patches:**
    *   Renames the original `steam_api(64).dll` to `steam_api_original.dll` and places the ReFix proxy as `steam_api(64).dll`.
    *   Deploys the Goldberg emulator backend as `steam_api_o.dll` so the proxy can dynamically load it.
    *   Targets Unreal/Godot root directories with `steam_appid.txt` and `winmm.dll`.
    *   Intercepts Epic Online Services by backing up `EOSSDK-Win64-Shipping.dll` to `EOSSDK_original.dll` and deploying a Dual-Mode proxy (`EOSSDK-Win64-Shipping.dll` / `RedboneEOS.dll`).
*   **Configuration Generation (`Generate-UNAE-ReFixIni`):** Builds a robust v3.0 `ReFix.ini` specifying arbitration modes, timeout thresholds, DiscoveryGroups, and P2P win-sock hooks.

## 3. Proxy DLLs (`steam_api_proxy.cpp`, `winmm.dll`, `EOSSDK-Win64-Shipping.dll`)
*   **Proxy Initialization & Bypasses:** The C++ `steam_api_proxy` is responsible for initializing the underlying original API or Goldberg emulator.
*   **AppId Masquerading:** The proxy intercepts `SteamAPI_RestartAppIfNecessary(unOwnAppID)` to always return `false`, bypassing anti-piracy restart triggers. It also reads `steam_appid.txt` and injects `SteamAppId` directly into the process environment block.
*   **License Spoofing:** Hooks like `SteamAPI_ISteamUser_UserHasLicenseForApp` and `SteamAPI_ISteamApps_BIsSubscribedApp` are manipulated (or passed to the Goldberg backend) to forcefully authorize DLCs and the base game.
*   **Dual Backend Loading:** The Proxy32 is designed to chain-load the `steam_api_o.dll` (which is installed as the Goldberg backend).

## 4. Registry Usage for Persistent Identity
The deployment logic specifically utilizes the Windows Registry to grant players a permanent identity, which is crucial for retaining inventory, stats, and saved games on LAN environments without central matchmaking servers.
*   **Hardware-Locked Hashing:** `deploy_helper.ps1` accesses `HKLM:\SOFTWARE\Microsoft\Cryptography` to extract the `MachineGuid`.
*   It computes an MD5 hash of this GUID (or a fallback string of `%COMPUTERNAME%_%USERNAME%`) and math-transforms it into a standard SteamID64 format (`76561197960265728 + accountId`).
*   This identity is synchronized into `force_steamid.txt` and `ReFix.ini`.

## 5. Steam Discovery Mechanisms
The tool dictates network routing depending on the deployment mode:
*   **Valve / Steam SDR:** Routes P2P packets via Steam Datagram Relay, disguising the session under the Spacewar AppId (`480`). This exploits Steam's infrastructure for WAN NAT traversal.
*   **LAN / Re:Goldberg Discovery:** Uses UDP multicasting/broadcasting on port `47584`. The discovery payload is targeted at IPv4 multicast group `239.255.71.84` (`DiscoveryGroup` in UNAE configuration). It accepts `CustomBroadcasts` arrays to traverse strict Virtual LANs like Radmin VPN or ZeroTier.

## 6. Portable Installation Logic
The deployment scripts implement robust isolation to ensure a game directory remains fully portable (e.g., transportable via USB drives):
*   **Local Saves Directory:** `deploy_helper.ps1` explicitly invokes `New-Item -ItemType Directory -Path $ExeDir\saves`.
*   **Goldberg Configuration Synchronization:**
    *   It writes `saves` to `$ExeDir\steam_settings\local_save.txt`.
    *   It auto-generates `$ExeDir\steam_settings\configs.user.ini` containing `[user::saves] local_save_path=saves`.
    *   This forces the Re:Goldberg emulator to redirect all `ISteamRemoteStorage` writes and offline save data to the local directory instead of `%AppData%`.
*   **Portable Firewall Helper:** `deploy_helper.ps1` generates a `Configure_LAN_Firewall.bat` in the target executable directory. When the user moves the portable installation to a new PC, they can simply double-click this `.bat` file to automatically authorize the `netsh advfirewall` UDP inbound/outbound rules required for LAN discovery on the new host machine.
